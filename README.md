# Hardware Protocol Emulation

HPE is a cross-platform protocol learning tool. The simulator core and CLI are written in C; the independent desktop GUI is built with Avalonia. I2C, SPI, SD/eMMC, USB 2.0 and PCIe devices are simulated entirely in software; no physical adapter or peripheral is required. The GUI communicates with the C simulator through a small C ABI bridge in `adapters/gui-c-api/`.

I2C has no universal enumeration procedure. `scan` probes the standard unreserved 7-bit address range and reports ACKs. A probe only discovers responding addresses; scenarios can then perform device-specific identification reads.

## Build from a clean checkout

The first build needs an internet connection, but no preinstalled development tools, package manager, Git, Go, Python, .NET SDK, CMake, Ninja, compiler or shell script. The checked-in native Go bootstrapper downloads pinned artifacts and verifies their SHA-256 hashes. Compiler SDKs (Go, Zig and .NET) belong under the ignored root-level `toolchain/` directory. Downloaded build programs such as CMake and Ninja, source-built helpers such as ccache, the vcpkg tree, package dependencies and all intermediate outputs belong under `build/`. In particular, CMake is currently downloaded as a prebuilt host program; it is neither generated by this project nor compiled from CMake source during the project build. CMake's generated build files (for example, Ninja files and caches) belong in `build/projects/`. Linux X11/font libraries are built into the project-local vcpkg tree. Ninja, .NET publish and vcpkg use the detected CPU count, or `HPE_JOBS` when set. ccache stores its cache in `build/ccache-cache/`.

Run the checked-in bootstrap executable for your host:

```sh
./bootstrap/bin/hpe-bootstrap-linux-x64 build
```

On Linux ARM64, use `bootstrap/bin/hpe-bootstrap-linux-arm64`. On Windows, run the matching executable from Command Prompt or a terminal:

```cmd
bootstrap\bin\hpe-bootstrap-windows-x64.exe build
```

Windows ARM64 uses `bootstrap/bin/hpe-bootstrap-windows-arm64.exe`. These small Go launchers are the only checked-in executables; they need no Go installation. They fetch and verify pinned Go, Zig, .NET, CMake, Ninja and (on Linux) Python distributions, then build ccache, native dependencies and HPE. They use all detected CPU cores; set `HPE_JOBS=8` to limit parallelism. Set `HPE_BUILD_ROOT` to place downloaded build programs, dependencies and intermediate files elsewhere; set `HPE_TOOL_ROOT` to relocate compiler SDKs. Final programs are installed to this checkout's platform-specific `install/<RID>/` directory. The bootstrap source is in `bootstrap/` and can be rebuilt with the downloaded Go SDK.

Every `build` command saves a complete, timestamped log under `build/logs/` while continuing to show output in the terminal. The exact log path is printed when the build starts and finishes. Set `HPE_LOG_DIR` to store logs somewhere else; this is useful when Windows build logs should be directly visible to WSL. For example, if the checkout is `C:\Users\admin\src\HardwareProtocolEmulation`, set `HPE_LOG_DIR=C:\Users\admin\src\HardwareProtocolEmulation\build\logs` in Command Prompt, then open `/mnt/c/Users/admin/src/HardwareProtocolEmulation/build/logs/` from WSL. The default location is relative to the checkout's `HPE_BUILD_ROOT` when that variable is set.

To check that developer tools are not being found on the host, Linux can run `PATH=/nonexistent ./bootstrap/bin/hpe-bootstrap-linux-x64 build`. From Windows Command Prompt, run `set PATH=%SystemRoot%\System32` and then invoke the Windows bootstrap executable above. The bootstrapper adds only its project-local tools back to the build process PATH. vcpkg's DLL deployment uses its bundled executable implementation; the legacy PowerShell deployment path is explicitly disabled.

The `Zero-tool build` workflow repeats this check on clean Linux and Windows hosted runners for pushes, pull requests and manual runs. The Windows job also starts the installed CLI, so it verifies a native Windows build and launch rather than only cross-compiling the bootstrap executable.

The final programs and runtime dependencies are placed under `install/<RID>/` (for example, `install/linux-x64/` or `install/win-x64/`): the CLI and GUI launchers, self-contained Avalonia app and .NET runtime under `gui/`, `libhpe_core` under `lib/` (or `hpe_core.dll` beside the Windows apps), examples under `examples/`, and fonts under `lib/fonts/`. GUI and .NET runtime files remain separate so they can be updated or inspected independently; the publish is not a single-file bundle. DejaVu Sans and Noto Sans SC are bundled for English and Simplified Chinese, with their licenses beside the fonts. Additional `.ttf` or `.otf` fonts can be placed in `install/<RID>/lib/fonts/`. Project toolchains are stored under the root `toolchain/`; dependency source, package installs, caches, and intermediate build artifacts stay under `build/`. Release builds omit debug data. Windows and Linux builds provide both GUI and CLI.

The bootstrap executable downloads compiler SDKs and build programs into ignored directories; ccache and native dependency libraries are compiled into `build/`. Git is not used by the build entrypoint. The pinned vcpkg source is converted to a filesystem registry so its version baseline does not need Git history. XZ, gzip and Zstandard extraction are implemented inside the Go bootstrapper. On Linux, GNU Make, Perl, a static BusyBox shell and its command applets are installed under `build/tools/build-tools/`; Autotools, Bison, Flex and gperf are built there with the bundled Zig compiler. The Linux helper build uses that private command directory instead of relying on the user's PATH. The installed Linux GUI launcher is also a static Go executable, so it does not need `/bin/sh`. Windows uses the checked-in Go bootstrapper and project-local compiler/build SDKs; no PowerShell bootstrap script is involved. “No preinstalled tools” does not remove operating-system runtime requirements: Linux still needs a compatible kernel and libc, and GUI use needs an active X11/Wayland/WSLg session; Windows uses its system APIs. The output targets the machine and operating system where its build entrypoint runs; this setup does not cross-compile Windows binaries from Linux or vice versa.

## Run

```sh
./install/linux-x64/hpe-cli --demo --trace i2c-trace.txt
./install/linux-x64/hpe-cli --scenario install/linux-x64/examples/i2c/i2c_basic.hpe --trace i2c-trace.txt
./install/linux-x64/hpe-cli --scenario install/linux-x64/examples/spi/spi_nor.hpe --trace spi-trace.txt
./install/linux-x64/hpe-cli --scenario install/linux-x64/examples/sdmmc/sd_emmc_blocks.hpe --trace card-trace.txt
./install/linux-x64/hpe-cli --scenario install/linux-x64/examples/usb/usb2_echo.hpe --trace usb-trace.txt
./install/linux-x64/hpe-cli --scenario install/linux-x64/examples/pcie/pcie_basic.hpe --trace pcie-trace.txt
./install/linux-x64/hpe-gui
```

The CLI prints decoded protocol events and device results. Its optional trace file records signal changes or packet/transaction events with protocol-specific fields and virtual nanosecond timestamps. The GUI places example selection and run controls in the top toolbar, with the scenario editor above the timing view and decoded-event list. Click a decoded record to move the green time cursor to that event. Choose English or 简体中文 from Settings → Language. In the timing panel, use the wheel to zoom around the pointer, middle-drag to pan, and Fit to restore the full trace. Signal values can be shown in binary, octal, decimal or hexadecimal. Device State opens a live memory view for the simulated devices.

## Scenario format

Scenario files are UTF-8 text. Blank lines and `#` comments are ignored. Numbers accept decimal or `0x` hexadecimal notation.

| Command | Meaning |
| --- | --- |
| `device NAME ADDRESS REGISTER_COUNT FILL` | Add an 8-bit register-mapped virtual I2C device. |
| `set ADDRESS REGISTER VALUE` | Initialize one device register. |
| `scan` | Probe addresses `0x03` through `0x77`. |
| `probe ADDRESS` | Probe an address; fail the scenario on NACK. |
| `expect-nack ADDRESS` | Probe an address; fail the scenario if it ACKs. |
| `write ADDRESS BYTE...` | Write bytes; the first byte selects the register and following bytes write sequential registers. |
| `readreg ADDRESS REGISTER LENGTH` | Set the register pointer, issue a repeated START, and read bytes. |
| `nack ADDRESS COUNT` | Make the next `COUNT` address phases to a device NACK. |
| `spi-device NAME CS MEMORY_SIZE FILL` | Add an SPI NOR flash with active-low chip select and initialized memory. |
| `spi-transfer CS MODE BYTE...` | Run one complete SPI frame (CS assertion through deassertion) in mode 0–3. Bytes are transmitted MSB first; the trace records MOSI and MISO. |
| `sd-card NAME BLOCKS FILL` / `emmc-card NAME BLOCKS FILL` | Create software-only SD v2 or eMMC storage (up to 2 GiB). Each block is 512 bytes; block pages are allocated only when written. SD cards at or above 2 GiB use the SDHC CSD and can negotiate block addressing. |
| `card-cmd INDEX CMD ARGUMENT` | Send one native SD/eMMC command and advance the card state machine. SD ACMD41 negotiates the supported OCR voltage window and HCS/CCS high-capacity mode; SD ACMD6 switches 1-bit/4-bit bus width. eMMC CMD6 supports EXT_CSD BUS_WIDTH and HS_TIMING byte writes. Also supports CMD12 stop, CMD18/CMD25 multiple-block transfers and CMD23 block counts. |
| `card-register INDEX CID\|CSD\|EXT_CSD` | Inspect synthesized CID/CSD images or eMMC EXT_CSD summary fields. The C API returns the raw 16- or 512-byte image. |
| `card-read INDEX BLOCK` | Read the next block after CMD17/CMD18; print its first 16 bytes. |
| `card-write INDEX BLOCK FILL_BYTE` | Fill the next block after CMD24/CMD25. The public C API can instead write all 512 caller-supplied bytes. |
| `usb-device NAME VID PID MANUFACTURER PRODUCT` | Create a USB 2.0 full-speed virtual device with standard descriptors, bulk endpoints 1 OUT/IN and interrupt endpoint 2 IN. |
| `usb-enumerate INDEX` | Reset and enumerate a virtual device: read initial/full descriptors, assign address, inspect configuration and strings, then set configuration 1. |
| `usb-control INDEX ADDRESS BMREQUESTTYPE BREQUEST VALUE INDEX LENGTH` | Execute a standard control request on endpoint zero. |
| `usb-bulk-out INDEX ADDRESS BYTE...` / `usb-bulk-in INDEX ADDRESS LENGTH` | Send data to bulk OUT endpoint 1; the virtual echo function returns it on bulk IN endpoint 1. |
| `usb-interrupt-queue INDEX BYTE...` / `usb-interrupt-poll INDEX ADDRESS` | Queue up to 8 report bytes and poll interrupt IN endpoint 2; an empty poll traces NAK and succeeds in the scenario. |
| `pcie-device NAME BUS DEVICE FUNCTION VID DID CLASS SUBCLASS PROGIF BAR0_SIZE GEN LANES` | Add a virtual Type 0 endpoint with one memory BAR and link capabilities. |
| `pcie-enumerate` | Train endpoint links through Detect/Polling/Configuration/L0 and discover vendor/device IDs. |
| `pcie-corrupt-next-tlp` | Inject a one-shot LCRC error to demonstrate NAK DLLP and same-sequence replay. |
| `pcie-cfg-read|write INDEX OFFSET WIDTH [VALUE]` | Access endpoint configuration space using aligned 1-, 2- or 4-byte accesses; writing all ones to BAR0 and reading it back probes the modeled aperture size. |
| `pcie-mmio-read|write INDEX OFFSET WIDTH [VALUE]` | Access BAR0 after enabling Memory Space in the Command register. |

Example:

```text
device eeprom 0x50 256 0xFF
device temperature_sensor 0x48 16 0x00
set 0x48 0x00 0x5A
scan
readreg 0x48 0x00 1
```

Devices exist only in simulator memory. Multiple devices may share an address to demonstrate conflicts; HPE reports a warning and models ACK/data as wired-bus behavior.

SPI scenarios support common NOR commands: Write Enable/Disable (`06`/`04`), Read/Write Status Register-1 (`05`/`01`), Read JEDEC ID (`9F`), Read Data (`03`), Page Program (`02`) and 4 KiB Sector Erase (`20`). BP2:BP0 and TB status bits protect a generic top or bottom fraction of the array; protected page programs and overlapping sector erases are ignored. Programming applies flash 1-to-0 behavior and wraps within a 256-byte page. Device IDs use a generic Winbond-like manufacturer/type and the configured capacity when it is an exact power of two. Timing is deterministic and currently uses a fixed 1 MHz clock. The model does not yet represent per-part protection maps, suspend/resume, deep power-down, quad/octal modes, electrical timing limits or vendor-specific command differences.

SD/eMMC scenarios model native command frames with CRC7, response frames, SD CMD0/CMD8/CMD55/ACMD41 initialization, eMMC CMD0/CMD1 initialization, identification and RCA selection, transfer-state selection, single and multiple-block CMD17/CMD18/CMD24/CMD25, CMD23 block counts, CMD12 stop, 512-byte storage, and block CRC16. Virtual card capacity is limited to 2 GiB, with written 512-byte pages allocated on demand. SD cards at or above 2 GiB expose CSD structure 1.0 and use block addressing. SD ACMD41 intersects the host voltage request with the modeled 2.7–3.6 V range and only reports CCS when the host requests high-capacity operation and the modeled card supports it. SD ACMD6 selects 1-bit or 4-bit width. eMMC CMD6 supports the EXT_CSD BUS_WIDTH SDR values (1-, 4- or 8-bit) and HS_TIMING legacy/high-speed write-byte modes and updates the live EXT_CSD image. CMD9/CMD10 expose synthesized CSD/CID response prefixes; the C API provides the complete 16-byte CID/CSD images, while eMMC CMD8 transfers a 512-byte EXT_CSD image with revision, device type and sector count fields. Register values are deterministic generic virtual-card values, not vendor identities. Identification command frames are traced at 400 kHz. Data blocks expand into clocked start, payload, per-DAT-line CRC16 and end-bit transitions at a modeled 4 MHz bus clock; writes also show the accepted data-response token and a fixed 250 µs busy period. The GUI labels each active DAT line for 1-, 4-, and 8-bit modes and can display the sampled data value on DAT0 in the selected radix. Tuning, high-speed electrical timing, card-dependent busy duration and many error-recovery paths remain simplified or unimplemented.

USB currently models USB 2.0 full-speed endpoint-zero standard control transfers, device/configuration/string descriptors, address assignment, configuration and configuration/interface/endpoint GET_STATUS. The single interface supports alternate setting zero; its configuration advertises remote wakeup and supports SET/CLEAR_FEATURE for that capability. Bulk endpoint 1 supports ENDPOINT_HALT SET/CLEAR_FEATURE, DATA toggles, ACK/STALL/NAK outcomes and CRC16-bearing packet events. Interrupt IN endpoint 2 supports queued reports, 10 ms host polling, NAK while idle, DATA toggles and endpoint halt recovery. Clearing endpoint halt resets that endpoint's data toggle to DATA0. A virtual bulk echo function exercises endpoint 1 in both directions. USB packets are expanded into SYNC/PID/token/data/handshake bit streams with token CRC5, data CRC16, full-speed NRZI, bit stuffing and EOP. The virtual full-speed host emits 1 ms SOF packets when packet traffic resumes across frame boundaries; the GUI plots the resulting D+/D− levels. Hubs, isochronous transfers, class requests, electrical tolerances and high-speed chirp negotiation are not implemented.

PCIe currently models software endpoints with Type 0 configuration headers, a basic Detect → Polling → Configuration → L0 link progression, fixed Gen4 x16 host capabilities, negotiated generation/width, config reads/writes, BAR0 size probing and memory-space gated MMIO. Config and memory request/completion events contain serialized 3-DW TLP headers, one-DW payloads where applicable, per-direction sequence numbers and LCRC values. Each modeled TLP is followed by a 6-byte ACK DLLP with AckNak_Seq_Num and CRC16; `pcie-corrupt-next-tlp` demonstrates an LCRC error, NAK DLLP and replay using the same TLP sequence. The GUI and CLI expose packet bytes and fields in the trace. TLP LCRC uses the 2-byte field containing the reserved nibble and sequence number followed by header and payload; DLLP CRC16 covers its type and three information bytes. The model does not render TLP/DLLP bits on lanes, model general link faults, replay timers or flow-control DLLPs, implement LTSSM ordered sets, PHY equalization, credit flow control, switches/bridges, capabilities beyond the small PCIe capability header, interrupts, DMA or hotplug. This is a functional enumeration/configuration model, not a complete PCIe implementation.

## C API and extension points

Include `hpe/hpe.h`, link `hpe_core`, create a simulation with `hpe_sim_create`, configure virtual devices, and call the protocol-specific `hpe_i2c_*`, `hpe_spi_*`, `hpe_block_card_*`, `hpe_usb_*` or `hpe_pcie_*` operations. The opaque simulation context owns devices and trace events until `hpe_sim_destroy`. Calls use deterministic virtual time and do not sleep in real time. I2C device authors can attach read/write callbacks for side effects or dynamic register values.

The simulator core is a shared library used by both applications. Protocol implementations, device models, and scenario parsing currently share internal simulator structures and are built into that core. As the supported protocol set grows, each backend should move behind a versioned plugin ABI so it can be loaded independently while the core owns common timing, tracing, and device registration contracts.

The I2C model currently covers 7-bit addressing, START/repeated START/STOP, byte reads and writes, ACK/NACK, deterministic 100 kHz timing, address scans, address conflicts and injected address NACKs. It does not model analog rise times, electrical loading or multi-master arbitration. The SPI backend currently models single-lane, full-duplex, 8-bit transfers in modes 0–3 and an SPI NOR device as described above.

USB and PCIe standards define additional PHY, link and transaction behavior beyond these teaching slices. HPE documents the current coverage and unsupported features for each backend; a protocol name alone does not imply full standards conformance.

Protocol references used for the implementation roadmap: [SD Association simplified specifications](https://www.sdcard.org/downloads/pls/) (the association identifies these as subsets of the complete specifications and notes that licensing may apply), [USB-IF USB 2.0 specification](https://www.usb.org/document-library/usb-20-specification), and [PCI-SIG PCI Express Base specification overview](https://pcisig.com/specification-overview/pci-express-base).

## Layout

```text
apps/cli/                 Cross-platform CLI application
apps/gui/Hpe.Gui/         Independent Avalonia desktop application
adapters/gui-c-api/       Stable C ABI bridge consumed by the GUI
include/hpe/              Public C API
src/engine/               Simulation lifetime, scheduling and event trace
src/devices/              Reusable virtual device models
src/scenario/             Scenario parser and runner
protocols/<name>/         I2C, SPI, SD/eMMC, USB and PCIe implementations
examples/<protocol>/      Protocol-specific teaching scenarios
tests/integration/        Cross-module protocol and simulator tests
assets/                   Fonts and application artwork
cmake/toolchains/         Compiler toolchain definitions
cmake/vcpkg/              vcpkg triplets and overlay ports
bootstrap/                Go bootstrapper source
third_party/              Optional source submodules for browsing upstream code; builds fetch verified snapshots directly
toolchain/                 Go, Zig and .NET compiler SDKs, ignored by Git
build/tools/               Downloaded CMake/Ninja/Python and source-built host tools
build/projects/            CMake-generated build systems and compiled project output
build/                    Dependencies, caches, downloads and intermediate build output
install/<RID>/            Final user-facing platform packages
```
